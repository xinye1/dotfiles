    The shape of it

    Not a step — the map. Three facts explain almost every surprise this repo can produce: what stow actually links, whether a directory is folded, and which of the two kinds of symlink you are looking at.

    Two kinds of symlink, two different owners

    The repo is a set of packages, each one mirroring the layout under $HOME. stow links a package's contents into $HOME — that happens once, at install. Inside the repo, a second and completely separate set of links picks which colour fragment is live, and theme moves those — that happens whenever you switch.

    Folded or unfolded — the one that catches everyone

    When stow links a package it makes a choice you do not see. If the target directory does not exist, it links the whole directory in one go. If a real directory is already there, it links each file individually. That decision is invisible afterwards and decides whether a file you add later appears on its own.

    One compositor, and everything hanging off it

    The packages are not peers at runtime. sway starts and owns most of the desktop, which is why a single swaymsg reload reaches so much of it — and why the theme switcher needs so little code of its own.

    03

    Clear the conflicts

    Stow will not replace a real file with a symlink. A fresh install already has all of these, so they must move aside first — this is the step that fails if you skip it.

    shell
    # ~/.bashrc comes from /etc/skel on every Arch install
❯ mv ~/.bashrc ~/.bashrc.bak

# Folded packages need the whole directory gone, not just its files
❯ for d in sway waybar mako fuzzel nwg-drawer gtklock foot; do
❯     mv ~/.config/$d ~/.config/$d.bak 2>/dev/null
❯ done

# gtk is tracked file-by-file, so move only the tracked files
❯ mv ~/.gtkrc-2.0 ~/.gtkrc-2.0.bak 2>/dev/null
❯ rm -f ~/.config/gtk-3.0/settings.ini ~/.config/gtk-4.0/settings.ini
❯ rm -f ~/.config/gtk-4.0/gtk.css ~/.config/gtk-4.0/gtk-dark.css

    The two gtk-4.0 symlinks point into /usr/share/themes/Arc-Dark. They must go, or stow can't place the libadwaita overrides.

    Two large images live inside stock config dirs — a 3.3 MB wallpaper in ~/.config/sway and a 22 MB lock screen background in ~/.config/gtklock. Neither belongs in a dotfiles repo. Move them to ~/Pictures/wallpapers if you want to keep them; this setup uses a solid Nord background instead.

    04

    Stow the packages

    Always dry-run first. Stow exits 0 even when it links to the wrong place, so the exit code proves nothing — the dry run's output is the real check.

    shell
    ❯ cd ~/repos/dotfiles
❯ stow -n -v bash vim bin starship alacritty foot htop waybar \
        sway kanshi gtk mako fuzzel nwg-drawer gtklock

    Every LINK: line must point at ../repos/dotfiles/…. Any CONFLICT means phase 03 was incomplete.

    shell
    ❯ stow bash vim bin starship alacritty foot htop waybar \
        sway kanshi gtk mako fuzzel nwg-drawer gtklock

    Check — every path must resolve inside the repo

    readlink -f ~/.config/sway~/repos/dotfiles/…
    readlink -f ~/.config/waybar~/repos/dotfiles/…
    readlink -f ~/.gtkrc-2.0~/repos/dotfiles/…
    readlink -f ~/.local/bin/theme~/repos/dotfiles/…
    shell
    ❯ for p in sway waybar foot mako fuzzel gtklock nwg-drawer htop; do
❯     printf '%-12s ' "$p"
❯     if [ -L ~/.config/$p ]; then echo "folded (symlink)"; else echo "UNFOLDED (real dir)"; fi
❯ done

    Eight lines, every one folded (symlink). This is the property the whole theming model rests on — each package's palette fragments live inside it, so no second package ever has to write into these directories.

    Use the [ -L ] test, not ls -la ~/.config | grep -E ' foo$'. ls prints a symlink as foo -> target, so the $ anchor matches only the unfolded case: the command prints nothing and looks like a pass precisely when folding is healthy, and speaks up only when it is broken.

    Three packages are deliberately not folded. nwg-look writes into the gtk dirs; alacritty's optional themes/ clone lives inside its own; and ~/.local/bin (the bin package) holds untracked binaries that folding would drag into the repo. For those three, a newly added file is silently absent until you run stow -R <pkg>.

    05

    Steps that can't be stowed

    Untracked clones and things that write outside $HOME.

    shell
    ❯ sudo papirus-folders -C nordic -t Papirus-Dark

    Yes, nordic — not nord. papirus-folders rejects nord outright. Despite the name the icons are genuine Nord: folder-nordic.svg is drawn in #5E81AC, #81A1C1 and #ECEFF4. The GTK theme is likewise named Nordic. Run papirus-folders -l to see the list.

    Gruvbox has no entry on that list at all. The switcher uses yellow as the stand-in, gruvbox's signature accent. This is the one place in the setup where the palette is approximated rather than matched — and the only reason theme ever needs sudo, since papirus-folders writes into /usr/share/icons.

❯ git clone https://github.com/itchyny/lightline.vim \
        ~/.vim/pack/plugins/start/lightline
❯ git clone https://github.com/arcticicestudio/nord-vim \

    shell
    ❯ git clone https://github.com/alacritty/alacritty-theme \
        ~/.config/alacritty/themes

    No longer required. alacritty.toml used to import nord.toml from this clone; it now imports its own switchable colors.toml fragment, so the repo describes the colours on its own. Clone it only to have other schemes to hand — and note it ships nord, nordic, nordfox and nord_light, three of which are not Nord.

    XDG_CURRENT_DESKTOP is empty in a stock session, and xdg-desktop-portal picks its backend from it. The sway config repairs this for systemd and dbus — which is what portals actually read — but only greetd can put it in sway's own environment. In /etc/greetd/config.toml:

    /etc/greetd/config.toml
    command = "env XDG_CURRENT_DESKTOP=sway sway"

    08

    Switching palettes

    Every colour in the setup is a named role, defined twice — once per palette — in a pair of fragments inside the package that owns it. A tracked symlink picks which fragment is live. Switching is flipping 17 of those symlinks.

    Press $mod+Shift+t. That is the whole day-to-day interface — it runs theme toggle. The bar, window borders, desktop, notifications, launcher, app grid and every GTK app change together; the three exceptions are listed below.

    Nothing needs a terminal, and nothing needs the repo. The rest of this phase is for when you want to see what it did, or when something looks wrong.

    shell
    ❯ theme                    # print the active palette
❯ theme gruvbox            # switch
❯ theme toggle             # the other one — what $mod+Shift+t runs

    Two flags. --no-icons skips papirus-folders, the only step needing sudo — use it in a script or over ssh, where there is no terminal to prompt on. --restart-terminals also restarts foot --server, applying the palette to the terminal immediately at the cost of every open shell.

    Each switch prints how many symlinks it flipped. It must say 17.

    shell
    ❯ sudo papirus-folders -C yellow -t Papirus-Dark   # gruvbox; -C nordic for nord
❯ theme gruvbox --restart-terminals                # name the palette — or just log out

    Only needed if the switcher said it skipped them. It runs papirus-folders itself when a terminal is there to take the sudo prompt, and prints the exact line to run when there isn't — over ssh, from a keybinding, or under --no-icons.

    --restart-terminals closes every open terminal. foot has no config-reload signal at all, so there is no gentler option. Skipping it leaves every terminal on the old palette, new ones included: $mod+Return runs footclient, and the server it connects to read its colours once, at startup. Nothing is right again until the server restarts or you log out.

    The flag needs a palette named alongside it. theme --restart-terminals on its own takes the no-argument path, prints the active palette and exits without restarting anything — see phase 09.

    Same sweep as phase 06, now under the other palette: $mod+d launcher · notify-send test · $mod+Shift+d drawer · the waybar clock tooltip, and scroll on it · $mod+f1 lock · thunar for GTK3 · any libadwaita app · $mod+Return terminal · Print · vim · ls.

    What each failure looks like: a black widget means a role the palette doesn't define — GTK CSS renders an undefined @name as black with no error. A surface still in the old palette means its fragment isn't named to the pattern and was never switched. A libadwaita app rendering light means ~/.config/gtk-4.0/gtk.css isn't linked.

    shell
    ❯ git -C ~/repos/dotfiles status --short   # 17 lines, all symlinks

    The symlinks are tracked, so the active palette is part of the repo's state. From a clean tree a switch produces exactly 17 modified paths and nothing else. Commit them or git checkout . — leaving them dirty makes every later diff noisy.

    shell
    ❯ theme                                    # what does it think is active?
❯ cd ~/repos/dotfiles && git status --short  # 17 lines, or 0 — never between
❯ theme nord --no-icons && theme gruvbox --no-icons

    A switch is all-or-nothing by construction: every fragment is checked to exist before any symlink moves, so a missing one aborts having changed nothing and names what's missing. If the tree shows some number other than 17 or 0 modified paths, something outside the switcher edited a symlink.

    Switching away and back re-flips all 17 from a known state. It is safe to run at any time and cannot half-apply.

    shell
    ❯ cd ~/repos/dotfiles/<pkg>/.config/<app>
❯ # write colors-nord.ext and colors-gruvbox.ext — same role names in both
❯ ln -sfn colors-nord.ext colors.ext       # relative and bare, never a path
❯ # point the app's config at colors.ext with its own include directive
❯ theme gruvbox --no-icons                 # must now say 18

    No code changes — the switcher finds its work by filename. The count going up by one is the confirmation; if it doesn't, the name doesn't match <base>-nord.<ext> / <base>-gruvbox.<ext> and the file will be silently left on one palette forever.

    If the package is unfolded — alacritty, gtk, vim, bin — the new files need stow -R <pkg> before they exist in ~ at all.

    Three things do not update immediately. foot — it has no config-reload signal, so open terminals and the running server keep the old colours until --restart-terminals or a logout. Running GTK apps — they read settings.ini once, at startup; restart the app. Folder icons — skipped when there is no tty for sudo; run the line the switcher printed. Everything else is live by the time the command returns.

    Never make the switcher a stow package. A theme-nord / theme-gruvbox pair writing into ~/.config/waybar would force stow to unfold that directory, and every themed package would lose the "new files appear for free" property checked in phase 04. Flipping a symlink inside the package leaves fold state untouched — which is why the fold table in the playbook is unchanged by any of this.

    Adding a themed application means adding two fragments and a symlink, and changing no code — the switcher discovers its work by filename. The sharp edge is the same fact from the other side: a file not named <base>-nord.<ext> / <base>-gruvbox.<ext> is silently never switched. There is no manifest to fall out of step with, and none to complain either.

    09

    How the switcher works

    Phase 08 is the procedure. This is the machine under it, in four parts: A what you type, B what happens inside the repo, C how that reaches the screen, and D what keeps it honest. Nothing here is needed to use the desktop; it is what you read before changing the switcher, or when it does something you did not expect.

    Register
    A

    The interface

    A1 · theme — the command surface

    One POSIX sh script, about 240 lines, at bin/.local/bin/theme in the repo and ~/.local/bin/theme on your PATH — the same file, linked there by stow bin. It calls nothing exotic: find, grep, sed, awk, readlink and ln. It is not a daemon and keeps nothing running.

    the whole interface
    ❯ theme                              # print the active palette, exit 0
❯ theme nord                         # switch
❯ theme gruvbox                      # switch
❯ theme toggle                       # the other one — what $mod+Shift+t runs
❯ theme -h                           # the header comment, printed back
❯ theme gruvbox --no-icons           # skip papirus-folders, the only sudo step
❯ theme gruvbox --restart-terminals  # also restart foot --server

    Anything that is not a recognised flag is taken as the target palette, validated against the list nord gruvbox. Every failure path prints theme: <reason> to stderr and exits 1; success is 0. That makes it safe in a script: theme gruvbox --no-icons || echo failed.

    Both flags need a palette named alongside them. With no target, theme takes its "just tell me the active palette" path and exits before the flags are ever acted on — so theme --restart-terminals prints gruvbox and restarts nothing, silently. Write theme gruvbox --restart-terminals. Naming the palette you are already on is fine: the switch is a no-op, and the flag still runs.

    In plain terms

    It is one script you run and that finishes — not a background service watching for changes. You type theme gruvbox, it edits some pointers on disk, tells a few programs to re-read them, and exits. Nothing keeps running afterwards.

    The one trap: the two options only do anything if you also name a palette. On its own, theme --restart-terminals just prints which palette you are on and stops — no error, no effect. It looks like it worked.

    B

    Inside the repo — how a switch is decided and made

    B1 · What one invocation does, in order

    Ten steps. Everything that can refuse the switch happens in steps 2–5, before any file on disk is touched.

    #StepWhat it does
    1parseFlags off the argument list; the remaining bare word is the target.
    2current_themereadlink on sway/.config/sway/theme.env. This is the only place "what is active" is ever read from.
    3resolvetoggle becomes the other name; the target is checked against the known list.
    4check_rolesThe two theme-*.env must declare identical variable names, and the two colors-*.conf identical set $var names. Refuses if not.
    5pre-flightFor every themed symlink, compute the sibling it would move to and assert it exists. Collects all misses and aborts naming them.
    6flipln -sfn per link, then print the count. It must say 17.
    7reload_desktopsway --validate, then swaymsg reload; then makoctl reload.
    8reload_iconsSource theme-<name>.env, and if the folder colour differs, sudo papirus-folders. Skipped under --no-icons, or printed as a line to run yourself when there is no terminal for the password prompt.
    9terminalsOnly with --restart-terminals: pkill -x foot, then foot --server.
    10advisoryWhat has not repainted yet, and the reminder that 17 tracked symlinks are now dirty in git.

    Steps 7–9 are the only ones that touch anything outside the repo, and none of them can run unless step 6 completed.

    In plain terms

    It is a batch job with a validation stage in front. It works out everything it is about to do, checks all of it, and only then writes — so a switch either happens completely or does not start. There is no state where half your desktop is Nord and half is Gruvbox.

    The closest thing in your world: validating a whole dataframe's schema before writing a single row, rather than discovering on row 40,000 that a column is missing and leaving a half-written table behind.

    B2 · How it finds its work — filenames, not a manifest

    There is no list of applications anywhere in the script. It searches the repo for symlinks whose target ends in -nord, -gruvbox, or those with an extension, and rewrites the name in place with shell parameter expansion — which is why both shapes work:

    the naming contract
    colors.css     -> colors-nord.css      # with an extension
.gtkrc-2.0     -> .gtkrc-2.0-nord      # without one
theme.env      -> theme-nord.env
colors         -> colors-gruvbox       # mako

    This cuts both ways, and the second way is the sharp one. Adding a themed application is two fragments and a symlink with no code change — the count simply goes from 17 to 18. But a file misnamed by one character is not an error: it is invisible. It will sit on one palette forever, and nothing will ever mention it, because nothing knows it was meant to exist.

    That is why phase 08 tells you to read the printed count. The count is the only feedback this design can give you.

    In plain terms

    The script has no list of what to switch. It works it out every time by looking at filenames — the way you would read every file matching data/*_2024.parquet rather than keeping a list of them in the code.

    Why that matters: a correctly-named new file is picked up for free, and a misnamed one is skipped in total silence. Same as the glob — if you typo the pattern you do not get an error, you get fewer files and no warning. So the number the command prints (17) is what you check, the way you would check a row count after a load.

    B3 · Where "the active palette" is stored — nowhere

    There is no state file, no environment variable, no cache. theme with no argument runs readlink on sway/.config/sway/theme.env and reports what it points at. The recorded state cannot drift from the real state because there is no recorded state — the symlink is both.

    Since all 17 symlinks are tracked in git, the active palette is part of the repo's committed state. From a clean tree a switch leaves exactly 17 modified paths, all symlinks. Any other number means something outside the switcher moved one.

    In plain terms

    Nothing writes down which palette is on. "Which one is active" is answered by looking at where a pointer points, so the answer can never be stale or disagree with what you are actually seeing.

    It is the same idea as a production alias in a model registry: there is no separate table saying which model is live — live is defined as whatever the pointer points at. You move the pointer to deploy, and you ask the pointer to find out.

    B4 · The rails that stop a half-switch

    RailStopsHow it shows up
    check_rolesA role defined in one palette but not the otherRefuses to switch, names the two files
    pre-flightA missing fragment aborting mid-flipRefuses, lists every missing file at once
    sway --validateReloading a config that will not parseRefuses to reload; the running desktop is untouched
    set -euA failed step being stepped overStops at the failure

    The first rail is the one worth understanding. GTK CSS renders an undefined @name as black — no warning, no fallback, no log line. A widget simply turns black, and the cause is a colour name missing from a palette file you were not editing at the time. It is close to undiagnosable from the symptom, so the switcher refuses to switch at all when the two palettes declare different role names. A blocked switch is the rail working.

    In plain terms

    The failure this design is most afraid of is not a crash — it is the silent wrong answer. If a colour name exists in one palette and not the other, nothing errors; the affected widget just goes black.

    That is the same shape as a join on a key that only exists on one side: no exception, no red text, just quietly wrong values downstream that you find weeks later. So the script does the equivalent of a schema check first — both palettes must declare exactly the same names — and refuses to run at all if they do not. If a switch ever refuses, it has just saved you from that.

    C

    Outside the repo — how the change reaches the screen

    C1 · What actually repaints, and what carries the colour

    Flipping symlinks changes files. Something still has to re-read them, and that is what the single swaymsg reload buys — sway owns more processes than it looks like:

    SurfaceRe-reads becauseWhen
    sway itselfconfig.d/theme does include ../colors.confon reload
    waybarsway owns the bar process and restarts it; style.css does @import url("colors.css")on reload
    nwg-drawerexec_always, so the reload re-execs iton reload
    GTK 3 / 4 appsexec_always scripts/import-gsettings pushes settings.ini into gsettingson reload, for apps started after
    makoexec, not exec_always — a reload will not restart it, so theme calls makoctl reload itselfon reload
    gtklock, fuzzel, vimThey read their config at launchnext launch
    screenshot overlay, keyhint popupThose scripts source theme.env when they runnext invocation
    footNo config-reload signal exists at allserver restart or logout
    Running GTK appsThey read settings.ini once, at startuprestart the app

    import-gsettings is doing more than it looks. It reads ~/.config/gtk-3.0/settings.ini — itself one of the 17 flipped symlinks — and pushes the theme, icon, cursor and font names into gsettings. It also derives color-scheme from gtk-application-prefer-dark-theme, which is the only key libadwaita (GTK 4) apps consult to decide light versus dark. Without that line they render light against a dark desktop no matter what settings.ini says.

    The three scripts that source theme.env at runtime do so for a structural reason: config.d/* is read alphabetically and theme sorts last, so a file earlier in the order cannot reference $accent — it is not defined yet, and sway fails with Invalid border color $accent. Anything earlier that needs a colour has to call a script that reads the palette at the moment it runs.

    In plain terms

    Changing the files is only half of it — each program still has to notice. They fall into three groups:

    Reload and they are correct (the bar, window borders, desktop, notifications, the app grid) — one command handles all of these. Correct next time you open them (lock screen, launcher, vim, the screenshot overlay) — nothing to do. Stuck until restarted (terminals, and any GTK app already open) — these read their colours once when they started and have no way to be told otherwise.

    Think of it as hot-reloading a config versus having to restart the kernel. Most things hot-reload; terminals need the restart.

    D

    Keeping it honest

    D1 · The tests

    shell
    ❯ cd ~/repos/dotfiles && sh tests/theme_test.sh

    Eight cases, thirty assertions, and the only tests in the repo — theme is the only piece here with enough logic to get wrong. They run the real script against a throwaway $HOME containing a miniature repo, with swaymsg, sway and makoctl stubbed to fail, so the live desktop is never touched and you can run them at any time.

    They pin the guarantees claimed above: that one invocation completes the whole switch, that a missing fragment leaves the tree untouched, that divergent role names refuse, that both filename shapes flip. Run them after any edit to bin/.local/bin/theme.

    In plain terms

    A safety net for editing the script. It fakes a whole home directory and a fake desktop, runs the real command against them, and checks the results — so running the tests cannot disturb the machine you are sitting at.

    They exist because this script already shipped one bug that made a switch need two runs. The tests were written to fail on that bug first, then the bug was fixed — so they are known to actually catch something, not just to pass.

    The palettes

    Adding anything new means picking a role and supplying both values. The desktop drifted into four incompatible palettes because each config was themed on its own; it carries two coherent ones now only because every colour is named by role. Note that Nord and Nordic are different schemes — alacritty-theme ships both, and the GTK theme is genuinely called Nordic.

    Gruvbox Dark

    desktop is the one role not drawn from the palette on the Nord side. Nord has nothing below nord0, so it is a hand-darkened #272B33; gruvbox ships exactly this idea as bg0_h. The desktop being one shade below the window background is what turns the gaps into visible channels.

    The two are not interchangeable in temperature. Nord's accent is a cool frost blue with warning a long way off in yellow; gruvbox's accent is the yellow, with warning one hue step away in orange. Warning states read as hotter under Gruvbox rather than as a different colour. That is gruvbox, not a mistake in the mapping.
